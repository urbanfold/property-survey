## Source and behaviour

- Canonical migration: `supabase/004_verified_registration_notifications.sql`.
- Guarded FRESH-only complete installer: `supabase/staging/004_registration_install_fresh.sql`, generated by `scripts/build_registration_staging_sql.py`. All guards and migration are in one transaction. It requires postgres/no simulated Auth claims, the exact staging baseline comment and absence of all registration tables/functions/two trigger names. The marker is not independent project identity; check the connection reference too. If objects exist, STOP, preserve them and prepare an exact upgrade diff; do not reset, rerun the baseline or bypass the guard. Root004 handles early-candidate reapplication locally but this is not permission to apply it over an unknown deployed schema.
- Worker shared source: `supabase/functions/_shared/registration.mjs`; wrapper: `supabase/functions/dispatch-registration-notifications/index.ts`; complete Dashboard index.ts: `supabase/dashboard/dispatch-registration-notifications.ts`.
- Dispatch is capped atomically at 5 new attempts/minute and 50/hour for ALL callers. Pending queue remains pending on 429. Counts use server claim time and include accepted/uncertain/sending attempts. `Retry-After` is seconds. Unchanged users never get multiple first-confirmation events.
- Claim/recovery use the same transaction advisory lock. A claim still sending after five minutes is moved to uncertain with worker_interrupted reason, never pending. No automatic replay. Claim timestamp remains for audit/rate accounting. Recovery runs on subsequent claims (including idle/rate-limited calls) or explicit service-only `recover_stale_registration_notifications()`. If nothing invokes either, no background recovery runs by itself.
- New worker uses THREE-argument `finish_registration_notification(event uuid, accepted boolean, claimed_at timestamptz)` and validates returned persisted state; no accepted response after a stale/mismatched claim. Two-argument finish remains service-only for early-candidate migration compatibility, not used by new worker. Late completion never overwrites uncertain. Existing attempts missing claim time are conservatively assigned migration time; review any deployed upgrade impact and pause old workers before a later approved upgrade.
- New worker logs only fixed component/build/event/allowlisted transport. No credentials, queue payload, email, raw error/config value or correlation/user ID. Logging failure cannot change delivery state. Claim timestamp is stripped from notification payload.
- Recipient fixed server-side to urbanfolduk@gmail.com. Body states registration email, server registration/verification dates and historical signup checkbox Yes/No/Not recorded. Explicit warning: unticked is not consent; consult current consent before marketing. No marketing-list integration.
- Optional, unchecked checkbox; only strict true boolean at initial Auth insertion requests opt-in. Current opt-in false until confirmation. Missing/null/string/malformed checkbox is false. Server-generated dates/text/version; later user_metadata edits cannot change original history. Verified users can opt out/re-opt in; unchanged repeated preferences do not duplicate audit. Old users are not backfilled or notified. Email change/reconfirmation produces no duplicate.
- Confirmation is Supabase Auth STATE: newly inserted already-confirmed accounts (admin/autoconfirm/OAuth) also queue under preserved candidate rules. Do not claim this proves a clicked email link. Production must explicitly review enabled signup/provider paths. No new restriction on existing Auth providers was silently introduced.
- Audit is protected by grants/RLS, not immutable against administrators; privileged Auth deletion cascades data. Retention/inbox access and future marketing unsubscribe/list synchronisation remain production decisions.

## Rollback / pause

- For worker delivery problems, pause its scheduler and set REGISTRATION_NOTIFICATION_TRANSPORT=disabled ONLY with configuration approval. These changes are not performed by this handoff.
- If the new triggers block signup/confirmation, separately approve `004_registration_pause_auth_triggers.sql`. It refuses until an explicit transaction-local acknowledgement is uncommented. It checks the staging marker/role and exact two trigger names, then disables ONLY urbanfold_auth_signup and urbanfold_auth_first_confirmation. No table/function drops, data deletions, credit updates, blanket Auth trigger disable, RLS weakening or cleanup008. Tests confirm it is guarded and works in an isolated DB.
- Preserve queue/audit/receipt data. New accounts created while paused have unrecorded original choice: no historic backfill/assumed consent on restart. Re-enable only after cause/fix/metadata review and approval.
- Roll back worker code only from a verified saved deployment export, preserving JWT/server auth. Retained tables/columns/helper overloads allow old code restoration, but old worker may not understand new 429/claim metadata; keep it disabled unless compatibility is reviewed. Do not restore the exposed browser webhook.
- A stale/interrupted/uncertain event is NOT automatically retried. Inspect exact receipt/provider evidence before any separate ID-scoped reconciliation or new delivery decision. Code rollback does not undo captures or make uncertain notifications safe to resend.
