# Isolated local staging client package

`python scripts/build_staging_client.py` writes `/workspace/urbanfold-staging-client/` and `/workspace/urbanfold-staging-client.zip`. It does not start a server, deploy, execute SQL, request credentials or contact an API. Artifacts are outside the repository. The builder copies current app/vendor sources and replaces only client initialization in the generated app with the local staging key bootstrap. Original app.js/index.html remain unchanged.

Fixed backend: `https://hexhtduvqzleoazusskh.supabase.co`. No production anon key or backend reference is included in generated app.js. A staging banner and restrictive CSP limit external connections/images to that project; local resources remain allowed. The bootstrap rejects secret/service-role inputs, rejects a legacy anon JWT with another project ref, clears the entered public key field and keeps the value in SDK memory only. New publishable keys cannot be decoded to prove project membership; the fixed endpoint still prevents requests to a different backend. Standard Auth tokens and existing app drafts may persist in the separate localhost origin; this does not introduce a new offline/recovery store.

Windows operator flow: download/extract the complete ZIP, double-click START-STAGING.cmd, keep its console open and use Chrome at http://localhost:8794/. The launcher uses built-in Windows PowerShell and a loopback-only TCP static server; it installs nothing, requests no admin rights, uses no Windows system configuration changes and serves an explicit file allowlist. The ExecutionPolicy override applies to the launched PowerShell process only; if Windows/organisation security blocks it, stop rather than disabling protections. Optional existing Python alternative is in the artifact READ-ME.txt. Do not open index.html directly as a file URL.

Enter only the STAGING project's publishable or legacy anon/public key into the local screen, never chat, URL or repository. Enter only staging dummy passwords. Do not use the live Pages app, configure production SMTP, click Buy, or Submit until the staging backend/notifications are ready. Signup/reset email and real admin exports remain separate configuration/tests. Localhost serves this laptop only; Android/Leica tests need an approved HTTPS staging origin.

Browser regression: build, then run `python tests/test_staging_client.py`. It checks wrong-project/role rejection, key-field clearing, login/resume with intercepted staging HTTP, and CSP rejection of another backend. This is not live Supabase isolation verification. The Windows launcher cannot be executed on the current Linux host and remains operator-validated; testing the same static content in Chromium with intercepted HTTP passed.

No GitHub push, PR state change, deployment, production SQL/Stripe/customer change or secret copy is included. Further authenticated API/storage tests require real dummy sessions in staging; UI filtering alone does not prove RLS.
